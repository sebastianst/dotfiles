# User Preferences

## Communication

- Refer to me as "Seb", not as "the user" or "the human"

## Version Control

- If in a JJ repository (`jj root` succeeds), even if colocated with git, use `jj` instead of git:
  - `jj status` and `jj diff --git` instead of `git status` and `git diff`
  - `jj f` to fetch
  - `jj commit -m "msg"` to commit
  - `jj bookmark create <name> -r @-` to create bookmarks
  - `jj p-` to push (pushes `@-`)
  - `jj squash` to amend changes into the previous commit
  - When creating PRs with `gh pr create`, specify `--head <bookmark-name>` since jj doesn't use git branches
- However, use git if in a worktree. The git worktree may be in a sub-directory (like `<repo>/.claude/worktrees`) of a jj repo, so `jj root` may return the outer repo root even though you're in a git worktree.
- Prefix branch/bookmark names with `seb/`
- Commit descriptions should have the form `<scope>: <desc>`. Avoid _conventional commit_ style `feat(…), fix(…), …` unless it is convention in the respective repository.

## Code Style

- Only add non-trivial code comments that genuinely help understanding
- Avoid comments that merely restate what the code does (e.g., "// Capture config values for use in the closure")
- Good comments explain *why*, not *what*
- Doc comments describe a symbol in its own terms — what it is and how to use it. Keep out of code docs: references to issues/plans, project phases or roadmap ("added in later changes", "Phase 2", "lands in a later phase"), and whether code "honors" some external intent. That context belongs in PR descriptions or commit messages, not the code.

## Development Style

- When fixing bugs, first write a test that fails, then fix the error (red/green TDD)
- Before pushing work, ask if I want to do a local review first

## Pull Requests

- Write terse PR descriptions. Put the most important information at the top. Don't repeat yourself, don't reiterate small details that the code review will reveal.
- Before addressing comments from AI reviewers (almanax-ai, etc.), ask whether they are relevant
  - This gives the user a chance to dismiss false positives at the PR before making unnecessary changes

## GitHub Issues and Artifacts

- Always identify AI-generated artifacts on GitHub with a "🤖 *Generated by Claude Code*" note at the end
  - When responding to comments/discussions, start with "🤖 *Claude says:* " _instead_ of the note at the end
- When creating GitHub issues with sub-issues, use the GitHub sub-issues API to link them as proper sub-issues (not just text references)
- Include GitHub permalinks (with commit hash) for all file path references in issues
- When opening PRs that fix/close an issue #<n>, end that PR's description with a "Fixes #<n>" or "Closes #<n>" comment.
